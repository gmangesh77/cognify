# ADR-005: Image-Spec Planner, Multi-Provider Stack, and Object Storage for Visuals

## Context and Problem Statement

Cognify's existing visual stack has three independent producers — `chart_generator.py`, `diagram_generator.py`, `illustration_generator.py` — each with its own contract, no awareness of the others, and no surface for editor control. Hero images use a single hard-coded prompt template piped to one provider (DALL-E 3) at one role (`hero`) at one placement (top of article). Editors cannot influence visual choice, regenerate a single visual, or refine a single image without re-running the whole pipeline. Generated bytes are stored as base64 inside the JSONB `visuals` column of `article_drafts`, which inflates row sizes and prevents CDN caching.

The competitor analysis (`COGNIFY_VS_IMPACTAI_REVIEW.md`) documents impactai's `feat/content-hub` branch shipping four patterns we lack:

1. A **per-section image planner** that picks N specs per section (role × style × placement) before any rendering happens.
2. A **visual-style catalogue** of 12 art-direction options applied as a separate prompt layer.
3. A **multi-provider stack** routing renders to Gemini Flash / Gemini 3 Pro Preview / Imagen 4 / DALL-E 3 by quality tier.
4. **MinIO/S3 object storage** producing public URLs instead of base64 payloads.
5. A **persona-aware planner prompt** with an explicit banned-cliché list ("no glowing AI brain", "no stock-photo handshakes", "no flat-design illustrations when photo style chosen").
6. **SSRF-guarded URL import** for editor-supplied custom images.

We need a decision that imports these patterns without breaking ADR-003 (CanonicalArticle as boundary) or ADR-004 (Transformer/Adapter publishing).

## Decision Drivers

- **CanonicalArticle stays the boundary** (ADR-003): no platform-specific knowledge in the content engine. Image plans are *content* and live on the canonical model; image rendering is *content*; publishing transforms but never plans.
- **Service-Layer pattern**: each visual concern (catalogue, prompt composer, planner, providers, storage, registry, SSRF guard) is a separate service. No direct DB calls from routes; no provider knowledge in the agent layer.
- **Open/Closed for providers**: adding a fifth provider is one new file under `src/services/visuals/providers/` and one register call — no edits to the planner, the agent nodes, or the API.
- **Observable cost**: every render records `cost_usd`, `latency_ms`, `model`, `prompt_used` as part of `ImageAsset.metadata` so the per-article cost endpoint (`/visuals/cost`) is a straight aggregation.
- **Single source of truth for the catalogue**: one Python module on the backend exposed via `GET /visuals/styles`. The frontend caches it at boot. No mirrored TypeScript catalogue (an explicit improvement over impactai's design, which suffers drift).
- **Storage-agnostic ImageAsset**: assets carry `image_url` *or* `image_b64`. MinIO/S3 produces URLs; local-dev with MinIO disabled produces base64. Publishing transformers consume whichever is present via a single `pickGeneratedImageSrc()` helper.
- **Security by default**: SSRF guard and MIME-sniff before any user-supplied URL or upload reaches storage. CIDR rejection list covers private, loopback, link-local, IPv6 unique-local, and IPv4-mapped IPv6 addresses.

## Considered Options

### Option A — Wholesale rewrite of the visual stack

Replace `chart_generator.py`, `diagram_generator.py`, `illustration_generator.py` with a single new module that handles all visual production through the planner.

- **Pros**: clean slate, single mental model, no legacy.
- **Cons**: throws away working chart/diagram code; risk of behaviour regression in publishing; large blast radius.

### Option B — Add the planner alongside existing producers, keep old contracts

Introduce a new image planner + multi-provider stack that runs *in addition to* the existing illustration/chart/diagram nodes. Settings flag `enable_image_planner` toggles whether the new path is active. The old nodes continue to function unchanged.

- **Pros**: zero behaviour regression; incremental rollout per article; easy revert.
- **Cons**: two parallel paths until rollout completes; extra LLM call per article (~3–5s); slight conceptual overhead.

### Option C — Bolt the planner into the existing illustration node

Reuse `illustration_generator.py` and extend it with role/style/placement awareness.

- **Pros**: single file change; smallest diff.
- **Cons**: violates SRP; the illustration node grows unbounded; no clean place for charts/diagrams to share planner context; impossible to A/B test old vs new.

## Decision Outcome

**Chosen: Option B — Add the planner alongside existing producers behind a feature flag.**

This phase ships:

1. **`src/services/visuals/`** — a new service module containing the catalogue, persona register, banned-cliché block, prompt composer, planner, image-render abstractions, registry, object-storage client, and SSRF guard. Charts and diagrams remain in `src/agents/content/` unchanged for now.
2. **Pipeline nodes**: `image_planner_node` (one Claude call per article producing `list[ImageSpec]`) and `image_render_node` (fanned-out provider calls with `asyncio.Semaphore(image_render_concurrency)`). Inserted after `seo_optimize` and before `generate_charts` in the LangGraph pipeline.
3. **CanonicalArticle additions** (ADR-003 amendment): two optional, backward-compatible fields:
   - `image_specs: list[ImageSpec] = []` — planner output, one entry per planned image.
   - `page_art_direction: str | None = None` — page-wide style guidance set by the editor.
   - `audience_persona: str | None = None` — surfaced from existing per-article params; threaded into the planner prompt.
   No existing field is reshaped or removed. Each rendered visual carries `spec_id` linking back to its plan.
4. **Object storage as the canonical asset transport**: `ImageAsset` exposes `image_url` (preferred when MinIO/S3 is enabled) and `image_b64` (fallback for local dev or storage outages). Publishing reads whichever is present; the `pickGeneratedImageSrc()` helper centralizes the decision.
5. **`enable_image_planner` settings flag** defaults to `True` only at the end of Phase 5 (frontend Studio rollout). Until then, articles generated under `False` keep the legacy hero-only behaviour — zero regression risk for existing flows.

**Boundary invariants (mirroring ADR-003 and ADR-004):**

- **Content engine has no platform knowledge.** Planner, providers, prompt composer, banned-cliché block, persona register, and storage all live under `src/services/visuals/` and consume only CanonicalArticle context. No imports from `src/services/publishing/`.
- **Publishing has no planner or provider knowledge.** Ghost/Medium/LinkedIn/WordPress transformers consume `ImageAsset` (with `image_url` or `image_b64`) and `ImagePlacement`. They never call providers, planners, or storage directly. The new `inject.py` helper (Phase 3) is shared between publishing transformers and the studio preview endpoint, but it operates on already-rendered assets — no provider calls inside.
- **Provider registry mirrors the TrendSource pattern (ARCH-002).** New providers register in `src/services/visuals/__init__.py::init_registry()`. No code outside that file knows the concrete provider classes.
- **Catalogue is server-authoritative.** The 12 styles, role defaults, persona register, and banned-cliché block live in Python under `src/services/visuals/`. The frontend boots, fetches `GET /visuals/styles`, and caches. There is no mirrored TS catalogue — eliminating drift by design.
- **Costs and provenance are first-class.** Every successful render appends `{spec_id, role_style, visual_style, aspect_ratio, placement_anchor, provider, model, prompt_used, cost_usd, generation_ms}` to `ImageAsset.metadata`. Audit and cost queries are pure aggregations over the canonical model.

## Consequences

### Positive

- Editors gain per-image control (regenerate, refine, replace, override style/provider/aspect, upload custom).
- A new publishing platform (e.g. WordPress, PUBLISH-002) requires only a transformer + adapter; the visual pipeline does not change.
- Storage is decoupled from the database — `article_drafts` rows stay slim, CDN caching becomes possible, MinIO/S3 lifecycle policies (90-day cold archive) handle growth.
- Single source of truth for the catalogue eliminates the frontend-backend drift class of bugs.
- Image cost is observable per-article and per-provider; budget caps enforceable.

### Negative

- One additional LLM call per article (the planner) — measured ~3–5s in impactai's instrumentation. Cached when re-running the same article.
- Operational complexity: MinIO/S3 must be provisioned in staging and production (Phase 6). Until then, base64 fallback is honest but inflates row sizes.
- Two visual paths (new + legacy) coexist until Phase 5 lands. Tests must cover both flag states.
- Provider rate limits and quota errors are now a real concern. Mitigated via Imagen 4 default-off, per-user budget caps, and friendly throttle UI.

### Risks recorded in plan §12

- Imagen 4 cost overrun (M, H) — gated behind `imagen_4_enabled`.
- SSRF via `/fetch-from-url` (M, H) — `safe_http.py` rejects private/loopback/link-local CIDRs, validates redirects.
- Malicious user upload (M, H) — MIME whitelist + magic-byte sniff + size cap.
- Provider catalogue drift — eliminated by single-source-of-truth design.
- HTML-refine endpoint produces broken markup (M, M) — `bleach` sanitization + diff-before-apply.

## Compliance with Existing ADRs

**ADR-003 (CanonicalArticle boundary)**: amended additively. New fields are optional and default-empty. Existing articles keep working without re-renders. Each rendered visual links to its plan via `spec_id`, which is a content-layer concept (not a publishing concept).

**ADR-004 (Transformer/Adapter publishing)**: untouched. New `inject.py` (Phase 3) is shared *content-layer* logic that publishing transformers may call to compose HTML, but it does not introduce platform code into the content engine. Each platform transformer remains a pure function `CanonicalArticle → PlatformPayload`.

**ARCH-002 (TrendSource Protocol & Registry)**: provider registry mirrors this pattern. `ImageProvider` is a `Protocol`; `ImageProviderRegistry` is the runtime container; `init_registry(settings)` is the wiring function.
